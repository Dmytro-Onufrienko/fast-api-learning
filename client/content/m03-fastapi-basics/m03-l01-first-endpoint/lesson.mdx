FastAPI turns a plain Python function into an HTTP endpoint using a
decorator, the same way Nest turns a decorated class method into one — but
the two frameworks get there very differently. Nest wires a controller
class, a method decorator, and parameter decorators together at startup
through reflection over TypeScript metadata. FastAPI reads your function's
**signature** directly: the parameter names, their type annotations, and
their default values are the entire contract. There is no separate DTO
class required, no `@Param()` / `@Query()` boilerplate — the type
annotation itself tells FastAPI where a value comes from and how to
validate it.

<Diff
  tsLabel="NestJS"
  pyLabel="FastAPI"
  caption="A route that reads a path parameter"
  ts={`@Controller('items')
export class ItemsController {
  @Get(':itemId')
  findOne(@Param('itemId', ParseIntPipe) itemId: number) {
    return { itemId };
  }
}`}
  py={`router = APIRouter()

@router.get("/items/{item_id}")
def read_item(item_id: int):
    return {"item_id": item_id}
`}
/>

Three things happen from that one Python function signature, with zero
extra code:

1. `item_id: int` becomes a path parameter, because `{item_id}` appears in
   the route template. FastAPI parses the URL segment and converts it to an
   `int` before your function ever runs.
2. If the URL segment can't be converted — `/items/abc` — FastAPI returns a
   `422 Unprocessable Entity` with a body describing exactly which field
   failed and why, before your function body executes. In Nest, this is
   what `ParseIntPipe` does explicitly; in FastAPI it's implied by the
   annotation.
3. The route, its parameter, and that parameter's type are recorded into an
   OpenAPI schema automatically. FastAPI serves it at `/openapi.json` and
   renders it as interactive docs at `/docs` — no `@nestjs/swagger`
   decorators, no separate `DocumentBuilder` setup.

<Gotcha title="A type annotation is not a suggestion">
In FastAPI, the annotation is the validation. `item_id: int` isn't a hint
for your editor — Pydantic (which FastAPI is built on) uses it at request
time to coerce and validate the incoming value. Get the annotation wrong —
say, `item_id: str` when you meant to accept only digits — and FastAPI
will happily accept `/items/abc`, because a string accepts anything. There
is no separate validation step to remember to add; the type *is* the
validation, which also means a sloppy type is a sloppy validator.
</Gotcha>

## Optional query parameters

A parameter that does **not** appear in the path template — and has a
default value — becomes an optional query parameter instead. `q: str |
None = None` reads almost like a TypeScript optional property, and that
resemblance is intentional: FastAPI leans on the same "the shape of the
value tells you what's allowed" idea that a `q?: string` field would in a
Nest DTO.

<Diff
  tsLabel="NestJS"
  pyLabel="FastAPI"
  caption="Adding an optional query parameter"
  ts={`@Get(':itemId')
findOne(
  @Param('itemId', ParseIntPipe) itemId: number,
  @Query('q') q?: string,
) {
  return { itemId, q: q ?? null };
}`}
  py={`@router.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}
`}
/>
